# Suisse Speech → OpenAI speech adapter

A small self-hosted HTTP adapter for using [Suisse Speech](https://suisse-speech.ch/docs/reference/)
with [sfortis/openai_tts](https://github.com/sfortis/openai_tts) in Home Assistant,
the OpenAI SDK, and other clients with a configurable OpenAI speech endpoint.
No OpenAI account or OpenAI API key is needed. Audio is generated by Suisse Speech.

## Home Assistant add-on

For Home Assistant OS / Supervised, install the prebuilt add-on (amd64 / aarch64):

1. Open **Settings → Add-ons → Add-on Store → ⋮ → Repositories**.
2. Add `https://github.com/splattner/openai-tts-suissespeech-adapter`.
3. Install **Suisse Speech OpenAI TTS**, configure your dialect, and start it.
4. Leave both add-on API key options empty for client-supplied Suisse Speech keys,
   or set both `suisse_speech_api_key` and `adapter_api_key` for server-held credentials.
5. In `sfortis/openai_tts`, choose **Custom**, endpoint
   `http://YOUR_HOME_ASSISTANT_IP:8000/v1/audio/speech`, model **`studio`** or **`swift`**,
   voice `anna`, and format `mp3`. Use the Suisse Speech key, or the configured adapter key.

See [add-on documentation](ha-addon/DOCS.md) for all options and troubleshooting.
Home Assistant Container/Core installations can use Docker Compose below instead.

## Quick start with Docker Compose

Requirements: Docker with Compose, and a Suisse Speech API key from the
[Suisse Speech console](https://console.suisse-speech.ch/).

```sh
cp .env.example .env
docker compose up -d --build
```

By default the client supplies its **Suisse Speech key** as an OpenAI-style
Bearer token. The adapter translates it into Suisse Speech's `X-API-Key` header.
The `.env.example` selects Swiss German with the Zurich dialect; edit `.env`
to change it. Without environment overrides the application uses `de-CH` / `standard`.

Test from a machine that can reach the adapter:

```sh
export SUISSE_API_KEY='sv_your_key'
curl --fail-with-body http://localhost:8000/v1/audio/speech \
  -H "Authorization: Bearer $SUISSE_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"tts-1-hd","input":"Grüezi! D Waschmaschine isch fertig.","voice":"anna","response_format":"mp3"}' \
  --output speech.mp3
```

A live key produces real speech and consumes your Suisse Speech allowance.
`sv_test_…` sandbox keys produce synthetic test audio, not the real voices.
The adapter never automatically retries paid synthesis requests.

## Home Assistant configuration

1. Install **OpenAI TTS** (`sfortis/openai_tts`) using its installation instructions.
2. Add an integration entry and choose the **Custom** provider preset.
3. Set the **API endpoint** to `http://YOUR_ADAPTER_HOST:8000/v1/audio/speech`.
   This is the **complete speech URL**, not just `/v1`.
4. Set the **API key** to your Suisse Speech API key (or your `ADAPTER_API_KEY`
   if using server-held credentials below).
5. Create a TTS agent with model `tts-1-hd` (studio) or `tts-1` (swift),
   voice `anna` or a voice from the live picker, and audio format `mp3`.
6. Use the resulting TTS entity with Home Assistant's `tts.speak` action.

`YOUR_ADAPTER_HOST` must be reachable **from Home Assistant**. `localhost` means
Home Assistant itself, not another Docker container or your laptop. Use your
Docker host's LAN address, or the Compose service name if both containers share
a Docker network. When using the add-on, use your Home Assistant host's LAN IP.

Example action (replace entity IDs):

```yaml
action: tts.speak
target:
  entity_id: tts.suisse_speech
data:
  media_player_entity_id: media_player.living_room
  message: "Grüezi! D Wösch isch fertig."
```

The Custom provider's **Extra JSON payload** can set per-agent Suisse options:

```json
{"language":"de-CH","dialect":"bern","style":"freundlich und herzlich"}
```

Home Assistant's selected language does not automatically select the Suisse
language/dialect: use adapter defaults or the extra payload explicitly.
Compact locales such as `de-CH-bern` can also be passed as `language`.
An explicit request `language` without `dialect` leaves dialect selection to
Suisse Speech rather than forcing the adapter's default dialect.

Home Assistant probes credentials with an empty speech request. The adapter
validates these against `/capabilities` and returns 400 for valid credentials,
or preserves the provider's rejection, without generating/billing audio.
`GET /v1/audio/voices` supplies the live Suisse voice catalogue for its picker.

## Other OpenAI-compatible clients

Use base URL `http://YOUR_ADAPTER_HOST:8000/v1` in clients that append
`/audio/speech` themselves. For example, with the separately installed Python `openai` SDK:

```python
import os
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8000/v1",
    api_key=os.environ["SUISSE_API_KEY"],
    max_retries=0,
)
with client.audio.speech.with_streaming_response.create(
    model="tts-1-hd",
    voice="alloy",
    input="Grüezi mitenand!",
) as response:
    response.stream_to_file("speech.mp3")
```

The streaming-response client interface works, but the adapter **buffers the
whole upstream response**: it does not offer low-latency token/audio streaming
or SSE. Clients must allow enough time for batch synthesis (120 seconds by default).

## Compatibility and mappings

| Client field | Suisse Speech behavior |
| --- | --- |
| `input` | `text`, up to 8,000 characters; no silent splitting |
| `model: tts-1` | `swift` |
| `model: tts-1-hd` or `gpt-4o-mini-tts` | `studio` |
| `model: studio` or `swift` | Passed through |
| Native Suisse `voice` ID | Passed through |
| OpenAI voice names, e.g. `alloy`, `nova`, `onyx` | All use `DEFAULT_VOICE` unless overridden |
| `instructions` | `style` (up to 600 characters); explicit `style` takes precedence |
| `speed` | Passed through, **0.5–2.0** only (Suisse's range, not OpenAI's wider range) |
| `response_format: mp3`, `wav`, `opus` | Native provider audio, no conversion |
| `response_format: pcm` | Native `pcm16`, forced to 24 kHz (OpenAI raw PCM contract) |
| `response_format: aac`, `flac` | Request WAV and transcode locally with ffmpeg |

The OpenAI voice aliases do **not** reproduce OpenAI voices. To customize mappings,
set e.g. `VOICE_ALIASES='{"alloy":"anna","nova":"YOUR_SUISSE_VOICE_ID"}'`.
Discover native IDs with `GET /v1/audio/voices`; available voices depend on the provider.
Unknown models are rejected rather than silently mapped.

Accepted provider-specific extra fields: `language`, `dialect`, `style`,
`sample_rate_hz`, `cache`, `cache_ttl_s`. Suisse Speech validates language/dialect,
voice and format-specific sample rates. Cache options only have an effect when
enabled on your Suisse Speech account. Unknown request fields are rejected.

Endpoints:
- `POST /v1/audio/speech` — binary audio or OpenAI-shaped JSON errors.
- `GET /v1/audio/voices` — live native voices in a `data` array.
- `GET /v1/models` — supported adapter model IDs (checks upstream authentication).
- `GET /healthz` — local process health only; does not check the provider/key.
- `GET /docs` — interactive adapter API documentation.

Provider error status codes and error codes are preserved, including the different
429 reasons and `Retry-After`. `tts.unknown_voice` becomes `voice_not_found` for
Home Assistant's voice-repair handling. Network failures return 502; timeouts 504.
This is speech synthesis compatibility only, not a general OpenAI proxy:
chat, transcription, realtime WebSockets, custom voice objects, and SSE are not implemented.

## Server-held provider credentials

To avoid putting your Suisse key in each client, set **both** in `.env`:

```dotenv
SUISSE_SPEECH_API_KEY=sv_your_provider_key
ADAPTER_API_KEY=your-long-random-client-secret
```

Clients then send `ADAPTER_API_KEY`; only the server uses the provider key.
The service refuses to start with a stored provider key but no adapter key,
so it cannot accidentally become an unauthenticated paid-synthesis proxy.
An optional `ADAPTER_API_KEY` without a stored provider key gates access, but is
also forwarded as the provider key, so normally use the default or set both.

Keep the service on a trusted network. Compose publishes port 8000 on all host
interfaces; restrict it with your firewall or bind a specific interface. If exposing
it outside your LAN, put it behind HTTPS, authentication and rate/concurrency limits.
HTTP carries credentials and spoken text unencrypted. There is no built-in per-user
quota or concurrency limit. Audio is buffered in memory; size/concurrency limits
at your reverse proxy are recommended for untrusted clients. The adapter does not
save text/audio or log credentials/request bodies; synthesis is sent to Suisse Speech.
Do not commit `.env`. Docker build context excludes it.

## Local development

Requires Python 3.12+ and [uv](https://docs.astral.sh/uv/).
ffmpeg is included in Docker; install it locally only if you need AAC/FLAC.

```sh
uv sync --locked --extra server
uv run uvicorn adapter.main:app --host 0.0.0.0 --port 8000 --env-file .env
```

The `server` extra installs uvicorn's optional dotenv support for `--env-file`.
Alternatively export the environment yourself and omit `--env-file`.

```sh
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

Tests use a mock Suisse upstream and do not need credentials or incur charges.
Real ffmpeg conversion tests run when ffmpeg is installed, otherwise they skip.
No live Suisse Speech request is made by the test suite.

Additional settings: `SUISSE_SPEECH_BASE_URL` (defaults to
`https://api.suisse-speech.ch/v1`) and `UPSTREAM_TIMEOUT_SECONDS` (120).
The latter is an HTTPX per-operation timeout, not an overall request deadline.

Protocol references: [Suisse Speech API / OpenAPI](https://suisse-speech.ch/openapi.json),
[OpenAI speech API](https://developers.openai.com/api/reference/resources/audio/subresources/speech/methods/create),
and [Home Assistant integration](https://github.com/sfortis/openai_tts).

## Releases and publishing

GitHub Actions follows the release-please and native multi-architecture build
pattern used by `splattner/digitalstrom-vdc-bridge`:

- CI runs tests, Ruff, add-on metadata validation, and an actual container smoke test.
- Conventional commits on `main` create/update a release-please pull request.
- Merging a release PR updates the Python, lockfile and add-on versions together,
  creates a GitHub release, and calls the reusable image publishing workflow.
- Images are published to GHCR for amd64/aarch64: the standalone image at
  `ghcr.io/splattner/openai-tts-suissespeech-adapter`, and the add-on at
  `ghcr.io/splattner/openai-tts-suissespeech-adapter/ha-addon` (version and `latest` tags).
- The build workflow also supports manual dispatch with an existing release tag
  for initial publication or rebuilding. The tag is checked out, not current `main`.

Repository Actions settings must allow creating pull requests. GHCR packages must
be public so Home Assistant can pull images without registry credentials.
Release publishing uses `GITHUB_TOKEN`; no personal access token is required.
Release-please PRs created with that token do not trigger other workflows;
push an update or manually run checks if you require CI on those PRs before merging.

For a local add-on container build, use the **repository root** as context:
`podman build -f ha-addon/Dockerfile -t suisse-addon:test .`
The Supervisor installs prebuilt images, not this source Dockerfile.
